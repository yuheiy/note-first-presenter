# 公開形態の検証はテスト層ではなく1つの自己完結したタスクに置く

公開形態（両パッケージを pack し、空のプロジェクトに実インストールしたもの）の検証を `verify:package` という単一の `vp run` タスク（`scripts/verify-package.ts`）に置く。**テスト層にはしない。** CI が変更ごとに、`prepublishOnly` が出荷の瞬間に、同じタスクを起動する。これに伴い integration 層（`test/*.test.ts`）を廃止し、4層を3層にした（ADR-0005）。

## 動機

ADR-0020 は #38 の「壊れる」方を直したが、壊れ方を検知する層は作らなかった。pnpm workspace ではシンボリックリンクの実体が `node_modules` の外なので、**公開形態を踏む層が1つも無いと、`npm i` した瞬間に落ちる CLI が全テスト層を通り抜ける**。この層の費用対効果は実証済み — ADR-0020 の作業で手順を手で1回踏んだだけで、テスト層では原理的に見えない実バグが3件出て、本 ADR の作業でもう1件出た（`cacheDir`、ADR-0016 に追記済み。**検証層が無いと自分で書いた原則の違反にも気づけない**、というこの ADR の動機の最短の実例）。

## テスト層にしない理由

対象はコードではなくリポジトリの**出荷物**であり、`*.test.ts` という鍵が意味を持つ範囲の外にある。実務上も、走らせたい頻度は「変更ごと」であって「`vp run test` を叩くたび」ではない。

## ゲートが主張すること、しないこと

主張は3つだけ: インストール済み CLI で `build` が完走し `dist/index.html` と `meta.json`（`resolved`）が出る / `export` が完走する / **`dev` が起動し `/nfp-data/meta.json` が `resolved` を返す**。`dev` を起動するのは、`resolveClientRoot()` が実インストールでは pnpm 仮想ストアの中を指し、その差が危険度を持つのが dev の connect middleware だけだから（`build` は同じデータをファイルに書く別コード）。`GET /` では足りない — SPA フォールバックは middleware が死んでいても 200 を返す。

**成果物の中身は主張しない。** 配信固有でない退行（404.html がコピーであること、テンプレートが効くこと等）はワークスペースの中と外で同じ理由で通り同じ理由で落ちるので、変更ごとに走る速い層が持つ。**型解決も global install も見ない** — 守る対象・設計した経路が現れてから足す。

**配信固有の事実はここでだけ assert し、それ以外は assert しない。**

## トリガーを2つ持つ

- **CI が push / PR ごとに**: 配信固有の壊れ方は publish 直前に知りたいことではない。
- **`prepublishOnly` が publish の瞬間に**: CI が保証するのは「そのコミットは良かった」であって「今 npm に送る実物が良い」ではない。npm publish は不可逆なので、将来リリースが CI に移っても外さない（CI の step は人が消せるが、`prepublishOnly` は publish というアクションそのものに縛られている）。

## 実装の要点（正本は `scripts/verify-package.ts` のコメント）

作業ツリーを汚さない（peer を tarball 2本の同時インストールで満たす、ADR-0013）/ `pnpm pack` は `prepublishOnly` を発火しないので再帰しない / 一時ディレクトリはリポジトリの外（中に作ると pnpm がワークスペースメンバーとして採用し、隔離が静かに消える）/ dev のポートは空きを確認してから渡す（Vite は使用中だと黙って隣に移る）。

`dev` の fail-fast（config 読み込みがサーバ起動より前）は型ではなくファイル分割で守る — 壊れたときの症状はエラーではなく「黙って既定値で動くサーバ」なので、`cli.ts` を1行に割って `vi.mock` で**順序そのもの**を assert する（`commands/__tests__/cliCommands.test.ts`）。型で担保する案は、構造型の `null` で迂回できるため退けた。

## Consequences

- `vp run test` は unit + e2e になり、ゲートはそこに含まれない。ゲートは `dependsOn` も `cache` も宣言しない — 自分で pack し、pack が `prepack` を発火するので、ビルドは測定対象そのものによって保証される（タスクキャッシュに「成果物は最新だ」と教えてもらうゲートは、自分が確かめるべき一点を他人に委ねる）。
- `prepublishOnly` が publish 時に vite-plus を要求する（素の `npm publish` は失敗する）。**それは正しい失敗**だが、将来のリリースワークフローは setup-vp を通す必要がある。

## Considered Options

- **起動スモーク（`--version`）にとどめる**: 却下。ADR-0020 の3件のうち `--version` で捕まるのは1件だけ。
- **成果物の中身の assertion を吸収する**: 却下。配信固有でない主張の退行が publish 前後まで遅れる。
- **`vp run test` に組み込む**: 却下。ADR-0005 が殺した「無規約な第3形態」の再来。
- **OS × パッケージマネージャのマトリクス**: 採らない。OS 固有で踏み得る箇所として特定できているのは demo の `node --watch-path` 1行だけ。必要が判明してから足す。
